# Issues - 5 August 2026

- On the design page, when I put a coupler in a tube, the dotted shadow line showing its position is visible in the tube it is in and the tube to the left, but not the tube to the right. The use case here is creating an electronics bay. Normally, the ebay coupler is shown as part of a "switch band" which is just a short body tube between the payload bay tube and booster tube. The switch band is designed to hold any external electrical switches needed to control the electronics in the electronics bay. The coupler it sits on extends into both the payload bay (forward tube) and the booster (aft tube).
- For motor delays, there should be an option for "none" or "plugged". If users are going to use electronics to deploy the parachutes, they will often remove the motor ejection charge to avoid the parachute being deployed inadvertently from a motor eject charge. Even if the user decides to fly without motor eject, the app should still calculate, and show on the results page, the optimal delay in case the user wants to fly a motor with motor eject at another time.
- In the results page, I am not seeing the "recovery weight". I see the metric in the CSV downloads, but not on the results page. Should we have some kind of dialogue box available for the user to decide which metrics they want to show on the results page? I think the most important tool is the CSV download (which has all the metrics), but, from a UI/UX perspective, it would be nice for the user to customize their results page to their personal preferences.
- I think we are flagging overstability too aggressively in the results pages. Most flights I am simulating get a red triangle safety flag because the static margin is too high. Let's discuss what margins give a red flag and which ones should be maybe flagged with something like a yellow warning flag. It feels strange that in the design page, we flag overstable with a green check mark, but in the launch results we flag it as a red triangle.
- The saved simulations are not tagged to a rocket, so it is impossible to tell what the sim was for. This could lead to a problem if users forget which sim was which and use the data for a different rocket. That could lead to a safety issue.
- I would like to see CP, CG, lengths and diameters out to 3 decimal places.
- In the preferences, we have a toggle for turning on/off "Rogers Modified Barrowman", but in the header we note our model uses "Extended Barrowman" and that does not change when we toggle that switch. So, what model is the default? Shouldn't the modified Barrowman be the default? If so, why are we toggling it? This is confusing and we need to clear that up because the way it is now, it is unclear which model the app is using. With all the modifications to the model, we have strayed from being a pure OpenRocket fork and that is okay (maybe even good) - perhaps it is time to revise the tag line and remove the part about using the "real OpenRocket physics engine" and just accept that what we have now created is a new thing.
- Are the units preferences being used in the motor results CSV downloads? When I did a batch motor simulation and downloaded the CSV, all the results in the CSV were in metric even though I had set a bunch of different unit preferences in the preferences dialogue.
- The RockSim exports have an error - the mass components are all being exported with the default mass (10g) instead of the overrides. This has a large effect on calculated CG in the RockSim files.
- RASAero exports do not seem to be working properly. When I try to load one of the exported files in RASAero, I get an error dialogue. The error messaging is in a file in this folder called RASAero_Error.txt.
- In the 2D view of the rocket, I should be able to view the aft end of the rocket so I can see if things like a cluster configuration are correct, or the motor tube is in the correct place, etc. Currently, there is no way to visualize a cluster configuration at all. You can set the cluster settings in the motor dialogue, but how does the user see what is happening when you play around with the layout, rotation and spacing settings?
- It appears our descent rate calculator may be incorrect or the details the app is getting from the parachute presets are incorrect. For example, when choosing the Fruity Chutes IFC-144-S in our app and simulating it with a 25 kg rocket, our app indicates a too-fast landing at 21.1 ft/s, but if I use Fruity Chutes' own descent rate calculator (https://fruitychutes.com/help_for_parachutes/parachute-descent-rate-calculator), it indicates a landing rate of 13.86 ft/s. That is a significant discrepancy. I can tell you from real experience that even the Fruity Chutes IFC-120-S is overkill for a 25 kg rocket. We need to either revise our descent rate calculator, determine if our presets are off, or minimize the reliability of our descent rate calculations and point the user toward the manufacturer's descent rate guidance. Either way, it may make sense to have a note saying something about not using our descent rate calculations as 100% true and to always follow the parachute manufacturer's guidance.
- When I get notifications (the notifications in the tan colored box that say things like "imported 4 motors" or something like that), the notification box should automatically clear when starting a new rocket design.
- Importing a cluster configuration from a RockSim file does not tag the cluster, it just imports all the motor tubes as separate, single motor layouts.
- Importing tube fins from RockSim files does not seem to work at all.
- I would like to explore the ability to add camera shrouds to the outside of body tubes and have the structures calculated into the CP. I, like many people, mount cameras to the outside of the body tubes to take videos of the flights. The shrouds holding the cameras tend to be easy to model because they tend to be geometric shapes that are made using 3D printing. We could probably use the same dialogue box as we use for freeform fin sets to capture the geometry of a camera shroud. For the CP calculations, wouldn't a camera shroud just act like a fin?
- In the design page, when I copy a component, it just gives me a duplicate of that component under the same parent component. What if I want to copy or move that component into a different parent component? For example, if I create a centering ring in one part of the rocket, I may want to copy it to many other parent components instead of having to recreate it every time I want a centering ring somewhere. Functionality needed - real cut and paste operations for components.
- We have no "undo" function right now. I would at least want to be able to click an undo button or hit Ctrl-Z to undo the last thing I did.
- In the 2D visualization of the rocket, all the inner components use the same exact dotted line shadow style, so it is impossible to see the difference between a mass component, a parachute, a centering ring, etc. There should be a visual difference between the components in the visual depiction. For example, a parachute component could use a small diagram of a parachute, a mass object could use a diagram of a weight block or kettlebell, etc. At a minimum, they should be different colors or something like that. Give me some suggestions on how to visually depict the internal components so users can differentiate them.
